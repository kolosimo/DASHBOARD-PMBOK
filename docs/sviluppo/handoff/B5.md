# Handoff B5: installazione su Windows Server 2019

Branch `agente/B5`. DB di test `cruscotto_test_b5` (e `cruscotto_test_b5r` per le prove di
ripristino), porta 3505.

## Cosa è fatto

| File | Contenuto |
|---|---|
| `bin/server.ts` | HTTPS diretto da Node: con `HTTPS_PFX_PATH` + `HTTPS_PFX_PASSPHRASE` ascolta in https (TLS ≥ 1.2, 1.3 disponibile) sulla `PORT` (443 nel modello di produzione), altrimenti http come prima. Errori chiari per PFX legacy (3DES/RC2) e password errata; avviso nei log sotto i 30 giorni alla scadenza (all'avvio e ogni 24 h); `HTTPS_REINDIRIZZA_DA_PORTA=80` facoltativo (301 verso https). Il server si crea nel hook `booting`, dopo il caricamento del `.env` |
| `commands/certificato_scadenza.ts` | `node ace certificato:scadenza [--avviso 30]`: SAN, emittente, validità, impronta, giorni alla scadenza. Uscita 0 ok, 1 in scadenza/scaduto, 2 PFX illeggibile. Esporta `leggiCertificatoPfx`, `giorniAllaScadenza`, `contestoDaPfx` (usate da `bin/server.ts`) |
| `database/seeders/produzione/configurazione_seeder.ts` | solo configurazione: discipline MEC/ELE/IDR/ANT, colonne e WIP 4/3, stati con pesi 0/20/50/70/85/100, 8 cause, `IMPOSTAZIONI_DEFAULT` (soglie e ore per persona marcate `di_esempio`). Nessuna commessa né utente. Idempotente (inserisce solo ciò che manca, per codice/chiave; rispetta gli `ordine` univoci), segnala le differenze (pesi o WIP cambiati dall'admin) senza toccarle. `environment = ['production']`: `npm run db:ricrea` in sviluppo lo ignora |
| `commands/db_inizializza_produzione.ts` | `node ace db:inizializza-produzione [--solo-migrazioni]`: `migration:run --force` + seeder produzione in una transazione, riepilogo per tabella e conteggio utenti/admin/commesse. **Rifiuta** un DB con i dati di esempio (`@climosfera.example`); nessuna opzione che cancelli dati |
| `deploy/pacchetto.mjs` | `npm run pacchetto` (vedi richieste): controlli (BOM degli script, dipendenze native), `node ace build`, copia senza test/e2e, `npm ci --omit=dev --omit=optional --ignore-scripts`, controllo `.node`/`binding.gyp` e percorsi lunghi, `versione.json`, zip scritto in Node (deflate, UTF-8, radice `cruscotto/`) + `.sha256`. ### Scelte

- **Config fuori dall'app**: `.env` e PFX in `C:\app\config` (ACL: Administrators, SYSTEM,
  account del servizio in sola lettura); l'app la trova con `ENV_PATH` (supportato da
  `@adonisjs/env`). Gli aggiornamenti sostituiscono solo `C:\app\cruscotto`.
- **Password del PFX nel `.env`** tra apici singoli con `\$` al posto di `$` (verificato:
  senza apici `#` tronca il valore, e AdonisJS interpola `$NOME`). installa.ps1 rifiuta
  password con apostrofi o `\$`.
- **Account del servizio** predefinito `NT AUTHORITY\LocalService` (impostato con
  `Win32_Service.Change`, che accetta la password vuota; `sc.exe` in PS 5.1 perde gli
  argomenti vuoti). Permessi con SID (`*S-1-5-19`), non nomi localizzati.
- **Ripristino come proprietario del DB** (`DROP SCHEMA public CASCADE; CREATE SCHEMA public`
  + `pg_restore --no-owner --no-privileges --single-transaction --exit-on-error`): niente
  password di `postgres` per ripristinare né per il ritorno automatico di `aggiorna.ps1`.
- **Pacchetto con `--omit=optional`**: `@adonisjs/vite` → `vite` (peer obbligatoria) e
  `@adonisjs/auth` → `@adonisjs/assembler` portano `rolldown`, `lightningcss`, `@ast-grep/napi`
  con binari **per la piattaforma su cui si crea il pacchetto** (Linux/Mac, inutili su
  Windows). A runtime in produzione non servono (provato: server e comandi ace partono dal
  pacchetto senza di essi). Il pacchetto ha 261 pacchetti npm, ~8.500 file, 10,7 MB,
  percorso più lungo 110 caratteri.
- Nessun IIS; PostgreSQL con `listen_addresses = 'localhost'` via `ALTER SYSTEM`, regole
  firewall che aprivano la 5432 disattivate e regola di blocco esplicita.
- Eventi in Application, sorgente "Cruscotto commesse" (ID in guida); attività pianificate:
  backup giornaliero (SYSTEM) e controllo certificato settimanale.

## Prove eseguite nel container

- `npm run pacchetto` (via `node deploy/pacchetto.mjs`) → zip verificato con `unzip -t`,
  `zipfile.testzip()` e `sha256sum -c`.
- Dallo **zip estratto**, con `ENV_PATH` su una cartella di config e `.env` generato da
  `env.modello`, `NODE_ENV=production`, DB vuoto: `db:inizializza-produzione` due volte
  (4/4/6/8/10 righe aggiunte, poi 0 aggiunte: idempotente), `certificato:scadenza` (0; 1 con
  `--avviso 120`; 2 con password errata o PFX legacy), avvio **https** con PFX di prova
  generato con openssl (`-keypbe/-certpbe AES-256-CBC -macalg sha256`): `/accesso` 200,
  verifica TLS con la CA di prova OK, TLS 1.3, asset CSS 200, cookie di sessione.
- PFX legacy (3DES/RC2) → avvio rifiutato con il messaggio "cifratura non supportata".
- Reindirizzamento http → https (301 con percorso e query).
- Avvio in http senza PFX (come in sviluppo): 200.
- Seeder: differenze segnalate (peso 25 invece di 20, WIP 5 invece di 4) senza modifiche;
  causa cancellata reinserita; DB con dati di esempio → uscita 1 senza toccare nulla;
  `NODE_ENV=production node ace db:seed` esegue solo il seeder produzione.
- Backup/ripristino con gli stessi comandi PostgreSQL degli script: dump custom, doppio
  ripristino su altro DB come proprietario, confronto MD5 tabella per tabella identico,
  trigger di `audit_log` presente.
- **PowerShell non eseguito**: `pwsh` è scaricabile ma il sandbox dell'agente ne blocca
  l'esecuzione. Revisione manuale mirata a PS 5.1: niente `??`, `?:`, `&&`, `||`; variabili
  seguite da `:` nelle stringhe scritte `${var}:`; output dei comandi nativi mandato a
  `Out-Host` per non inquinare i valori restituiti; callback TLS in C# (`Add-Type`) invece
  di uno scriptblock; niente argomenti vuoti a `sc.exe`; `$ErrorActionPreference = 'Stop'`
  e `Set-StrictMode 2.0`. **Da provare sul server al Gate 2** (vedi limiti).

`DB_DATABASE=cruscotto_test_b5 PORT=3505 npm run verifica`: typecheck OK, lint OK,
dipendenze native OK, unit 110/120 (i 10 falliti sono `tests/unit/domain/avvisi.spec.ts`,
"non implementato", attesi finché B1 non consegna), funzionali 194/194.

## Dipendenze da altri branch

- **B6** (account locali): `env.modello` usa `AUTH_MODE=locale` e `SESSION_INATTIVITA`;
  `installa.ps1` chiama `node ace utenti:crea-admin --email --nome` (comando di B6). Senza
  B6 l'avvio con `AUTH_MODE=locale` fallisce la validazione di `start/env.ts`. Nessun
  conflitto di file con B6 (`commands/` ha nomi diversi).

## Richieste all'orchestratore

1. `package.json` → `"pacchetto": "node deploy/pacchetto.mjs"` negli script.
2. `start/env.ts` (facoltativo, per documentazione e validazione):
   `HTTPS_PFX_PATH: Env.schema.string.optional()`, `HTTPS_PFX_PASSPHRASE: Env.schema.secret.optional()`,
   `HTTPS_REINDIRIZZA_DA_PORTA: Env.schema.string.optional()` (string: nel modello il valore
   può essere vuoto). Oggi `bin/server.ts` li legge
   da `process.env` (il `.env` è già caricato nel hook `booting`), quindi funziona anche
   senza. In `.env.example` le tre righe commentate.
3. Voce admin "certificato HTTPS" (A1/orchestratore): una riga in *Admin* con giorni alla
   scadenza e semaforo (sotto 30 giorni). Consiglio di spostare `leggiCertificatoPfx` e
   `giorniAllaScadenza` da `commands/certificato_scadenza.ts` a `app/shared/certificato.ts`
   (TS puro, nessun DB) e importarli da lì in comando, `bin/server.ts` e pagina admin.
4. `CLAUDE.md` (tabella comandi): `npm run pacchetto` → zip per Windows Server in
   `tmp/pacchetto/`; `node ace db:inizializza-produzione`; `node ace certificato:scadenza`.
5. `docs/sviluppo/ambiente.md` dice ancora "in produzione EDB su Windows Server 2022":
   ora è **PostgreSQL 17 EDB su Windows Server 2019**.
6. `docs/sviluppo/proprieta-file.md`: aggiungere `database/seeders/produzione/**`,
   `commands/db_inizializza_produzione.ts`, `commands/certificato_scadenza.ts`,
   `deploy/pacchetto.mjs`, `bin/server.ts` (parte HTTPS) → B5.

## Limiti noti

- Script PowerShell **mai eseguiti** su Windows (solo revisione): al Gate 2 eseguire
  nell'ordine `installa.ps1` → `servizio.ps1 stato` → `backup.ps1` → `ripristino.ps1
  -DbDestinazione cruscotto_prova` → `aggiorna.ps1` con un secondo pacchetto → prova del
  ritorno automatico (es. pacchetto con una migrazione che fallisce). Punti da osservare:
  `Expand-Archive` (lento: ~8.500 file), `Win32_Service.Change` con LocalService,
  `Export-PfxCertificate -CryptoAlgorithmOption` (se il parametro manca su 1809 si usa la
  procedura grafica o OpenSSL, già in guida).
- WinSW 2.x: `delayedAutoStart` è attivo per la sola presenza dell'elemento; l'arresto
  manda Ctrl+C e chiude il processo dopo 20 s. `bin/server.ts` ascolta SIGINT solo sotto
  pm2 (codice originale): sotto WinSW Node termina subito (le transazioni aperte vengono
  annullate da PostgreSQL). Un arresto più morbido richiederebbe
  `app.listen('SIGINT', …)` anche fuori da pm2 (da valutare).
- Il controllo della scadenza nei log e l'avviso settimanale usano i 30 giorni fissi.
- Il pacchetto si crea su Linux/Mac/Windows indifferentemente perché non contiene binari
  nativi; se in futuro una dipendenza di **runtime** avesse binari per piattaforma, il
  pacchetto andrebbe creato su Windows (il controllo `.node` lo bloccherebbe).
- `aggiorna.ps1` non gestisce il cambio di versione di Node: è una procedura a parte
  (in guida).
