# Handoff A3 — Flusso e Kanban

Branch `agente/A3`. Nessun file condiviso modificato: le modifiche necessarie sono
nella sezione "Richieste all'orchestratore".

## Cosa è fatto

- **Formule** (`app/domain/flusso.ts`, corpi): `workItemAge`, `cycleTime`, `throughput`,
  `cfd`, `controllaPassaggioStato`, `sforaWip`. Date sempre in Europe/Rome tramite
  `#shared/calendario`. I 32 test T1 di `tests/unit/domain/flusso.spec.ts` sono verdi.
- **CambioStatoService** (`app/modules/flusso/cambio_stato_service.ts`): unico punto che
  scrive `elaborati.stato_id`, `elaborati.stato_dal` e `transizioni_elaborato`.
  - Un solo stato avanti alla volta; salto → `PassaggioNonAmmesso` (422).
  - Indietro (anche di più stati) solo con motivo non vuoto; il motivo va nella transizione.
  - WIP: se la colonna di arrivo sfora (`sforaWip`), serve `confermaWip` **e** un motivo,
    altrimenti `WipDaConfermare` (422). Confermato: `wip_sforato = true` nella transizione e
    voce di audit `kanban.wip_sforato` (colonna, limite, conteggio, stati, motivo).
    Gli spostamenti dentro la stessa colonna non controllano il WIP.
  - `aggiornaConVersione` con audit `elaborato.stato_cambiato` → 409 su doppio spostamento.
  - Lock consultivo PostgreSQL per commessa (`pg_advisory_xact_lock(3, commessaId)`) così
    i conteggi WIP restano coerenti con spostamenti simultanei.
  - `pubblica(commessaId, 'elaborato.stato_cambiato', { elaboratoId, statoId })` dopo il commit.
  - Stato e `avvenuta_il` della transizione usano lo stesso istante (`stato_dal`).
- **Stati per posizione** (`stati.ts`): gli stati si confrontano per posizione nella
  sequenza ordinata (0 = iniziale), così la regola vale anche con ordini non consecutivi.
  Lo stato finale è l'ultimo con `finale = true` (altrimenti l'ultimo in ordine).
  Limite WIP effettivo = `limiti_wip_commessa.limite` se c'è, altrimenti `limite_wip_default`.
- **Query** (`queries.ts`): `riepilogoFlusso(commessaId, oggi)` implementata (una query per
  le schede con AC, una per la configurazione, una per le transizioni), più
  `transizioniCommessa` e `serieCfd(commessaId, dal, al)`. `SchedaKanban` ha in più
  `dataFissa` (aggiunta compatibile).
- **Pagina** `/commesse/:id/flusso` (Edge + HTMX + Alpine, testi del prototipo):
  - KPI: in lavorazione, throughput 8 settimane, cycle time medio, elaborati fermi
    (soglia `flusso.giorni_elaborato_fermo`, "fermo" se età ≥ soglia, come in `avvisi.ts`);
  - colonne da `colonne_kanban` con conteggio/limite; colonna oltre il limite evidenziata
    (`.col.over`) con "oltre il limite WIP";
  - schede con codice, classe di servizio (pill senza pallino, così non si confonde con i
    semafori; data fissa con la data), disciplina e stato, età in giorni (rossa se ferma),
    ore registrate su budget (`formato.ore`);
  - frecce ← → (form HTMX; ← chiede il motivo con `window.prompt` in `hx-on::config-request`);
  - drag&drop HTML5 con `setData` (Firefox): il rilascio manda la colonna; il server avanza o
    arretra di uno stato solo se lo stato adiacente è in quella colonna, altrimenti risponde
    422 con il messaggio (anche come toast), per esempio "si sposta uno stato alla volta.
    Prima completa lo stato "Calcoli e dimensionamento" con la freccia →";
  - sforamento WIP: finestra modale (`<dialog>` aperta con Alpine) con motivo obbligatorio,
    "Conferma lo spostamento" e "Annulla";
  - 409: la board aggiornata con il componente `conflitto` in cima (e toast da `HX-Trigger`);
  - throughput (barre SVG) e CFD (aree SVG impilate, geometria dalla funzione pura
    `grafico_cfd.ts`), ultime 8 settimane fino a oggi;
  - tempo reale: `#flusso` si ricarica da `/commesse/:id/flusso/frammento` su
    `evento-commessa` e `polling-commessa`.
  - senza JavaScript i form funzionano (redirect alla board dopo lo spostamento).
- **Permessi** (`permessi.ts`, abilità `spostaElaborati`): admin, PM della commessa,
  membri con ruolo `progettista` o `verificatore`. Direzione, osservatori e non membri: board in
  sola lettura (nessuna freccia, schede non trascinabili) e 403 sulla POST. La 403 è
  esplicita (`response.abort`) perché `bouncer.authorize` su una POST da form fa redirect.
- **Test** (`tests/functional/flusso/`, 27 test): servizio (avanti, salto, indietro con e senza
  motivo, WIP con conferma e audit, stessa colonna, colonna senza limite, 409, 404, nascita),
  HTTP (pagina per ruolo, frammento, frecce, drag&drop coerente e non, conferma WIP, 409 fra
  due utenti, 403, 404, fallback senza HTMX), `riepilogoFlusso` (ELE-SC-201 età 15 al
  24/09, cycle time medio 28 giorni, throughput W39 = 1) e CFD (serie e geometria).
- Controllato a mano nel browser (Chromium di Playwright, tema chiaro e scuro): frecce,
  prompt del motivo, modale WIP, messaggio del drop non coerente.

## Stato iniziale di un elaborato nuovo (per A1, modulo anagrafiche)

A1 inserisce l'elaborato ma **non** sceglie lo stato: usa il servizio nella stessa transazione.

```ts
import CambioStatoService from '#modules/flusso/cambio_stato_service'

await db.transaction(async (trx) => {
  const iniziale = await CambioStatoService.statoIniziale(trx) // { statoId, statoDal }
  const el = await Elaborato.create(
    { ...campi, statoId: iniziale.statoId, statoDal: iniziale.statoDal },
    { client: trx }
  )
  await CambioStatoService.registraNascita(el, utenteId, trx) // transizione null → iniziale
})
```

`registraNascita` serve a CFD e cycle time: senza, l'elaborato non compare nel CFD.
Anche l'import CSV deve chiamarla per ogni riga. Nessun altro modulo scrive `stato_id`.

## Limiti

- `npm run verifica` **non** è verde su questo branch per colpa di test T1 di altri moduli:
  i 63 test di `evm`, `lps` e `avvisi` falliscono con "non implementato" (corpi di A5, A2, B1).
  Typecheck, lint, dipendenze native, i 32 test T1 del flusso e tutti i 64 test funzionali
  sono verdi. Dopo il merge di A2, A5 e B1 la verifica dovrebbe essere verde.
- AC delle schede: letto con una somma su `registrazioni_ore` dentro la query del Kanban
  (`LEFT JOIN LATERAL`), perché `oreCommessa` di A4 non è ancora implementata e servirebbe
  una query per settimana. È una lettura, non una scrittura, ma è una lettura incrociata:
  vedi richiesta 4.
- CSS del modulo in un blocco `<style>` dentro `_flusso.edge` (colonna sotto il drag,
  modale, colori del CFD): vedi richiesta 3.
- Il CFD e il throughput coprono le ultime 8 settimane; nessun filtro di periodo.
- `controllaPassaggioStato(da, a)` con `da = a` restituisce un errore ("già in questo
  stato"): il drop sulla stessa colonna non chiama il servizio.
- `cycleTime`: se manca l'uscita dallo stato iniziale (elaborato nato già avviato) si usa la
  transizione di nascita in uno stato successivo; se l'arrivo allo stato finale precede
  l'inizio non si conta.
- Nota operativa: `.env.test` fissa `DB_DATABASE=cruscotto_test` e `PORT=3339`; lanciare
  `node ace test` senza le variabili usa il DB e la porta condivisi. All'inizio l'ho fatto per
  alcune esecuzioni (schema ricreato con il seed su `cruscotto_test`); poi sempre con
  `DB_DATABASE=cruscotto_test_a3 PORT=3431`.
- Il drag&drop con `page.dragAndDrop` di Playwright a volte parte dalla scheda sbagliata
  (comportamento di Playwright con HTML5 DnD); con `mouse.down/move/up` funziona. Per gli e2e
  usare le frecce o il mouse a passi.
